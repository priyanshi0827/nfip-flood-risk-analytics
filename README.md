# NFIP Flood Risk & Underwriting Analytics

Segment-level loss-ratio, claim-cycle-time and coverage-adequacy analysis over
the National Flood Insurance Program: **2.7M claims** and **74.7M policy
transactions** from FEMA's OpenFEMA API, modelled in DuckDB and published as a
Tableau dashboard.

The question behind it: *which flood-insurance segments lose money, why, and is
the mapped flood zone actually a good predictor of loss?*

---

## Why this data

FEMA publishes the full redacted NFIP book of business. That makes it one of
the very few places you can compute a real loss ratio - premium and paid losses
on the same population - on a portfolio of this size, without a carrier's
internal data.

| Dataset | Version | Records | Source |
|---|---|---|---|
| NfipClaims | 3 | 2,725,989 | OpenFEMA bulk parquet |
| NfipPolicies | 3 | 74,739,461 | OpenFEMA bulk parquet |
| NfipMultipleLossProperties | 1 | 240,651 | OpenFEMA API |

Field names and code values were pulled from FEMA's own metadata endpoint
(`/api/open/v1/OpenFemaDataSetFields`) rather than transcribed from
documentation - see `docs/DATA_DICTIONARY.md`. `src/fetch_schema.py`
re-fetches them, and `src/build_db.py` fails loudly if a required column has
disappeared.

## Running it

```bash
pip install -r requirements.txt

python src/fetch_schema.py                    # refresh schema from FEMA
python src/download_data.py                   # ~75M rows; --skip-policies for a fast first pass
python src/build_db.py                        # build the DuckDB warehouse
python notebooks/01_eda.py                    # exploratory pass -> outputs/eda_report.md
python src/run_analysis.py                    # write outputs/*.csv for Tableau
```

Run the EDA before designing anything visual. It reports field completeness,
how much of the data falls through the code mappings, and how well the two
files line up - all of which decide what the dashboard can honestly show.

The policies file is large. `--skip-policies` gets the whole claims side
working in a couple of minutes if you want to check the pipeline first.

## The analytical problem worth talking about

**Claims and policies cannot be joined.** FEMA redacts the policy identifier,
so there is no key linking a claim to the policy that produced it. Every
loss-ratio number therefore comes from aggregating *both* sides independently
to a shared grain - `state x flood-zone class x occupancy group x year` - and
taking the ratio of the aggregates.

That is an approximation, not a record-level truth, and it has consequences:

1. **Ecological inference.** A high loss ratio in a cell describes the cell,
   not any individual policy inside it. Cells with few policies are suppressed
   (`HAVING SUM(policy_count) >= 1000`) rather than reported as noise.
2. **Administrative error records.** Non-payment reason codes 98 (error,
   delete claim) and 99 (erroneous assignment) are corrections, not declined
   claims. They are flagged as `is_error_record` and excluded from every
   aggregate rather than deleted, so the count stays auditable.
3. **Segment drift.** A property can be rated in zone AE in the policy file and
   appear with a different current zone in the claims file after a map
   revision. Those losses land in a cell with no matching exposure. The mart
   uses a `FULL OUTER JOIN` and flags them as `loss_without_exposure` instead
   of dropping them - a `LEFT JOIN` from exposure silently loses them, which is
   the first bug I hit and the reason total paid losses now reconcile exactly
   against `v_claims`.

## Known limitations, stated up front

- **Written, not earned premium.** Exposure is aggregated by
  `policyEffectiveDate` year and each renewal is its own transaction. This is
  written premium by policy year, not earned exposure. For a true accident-year
  loss ratio you would need to earn premium across the policy term.
- **The policy file does not reach back as far as the claims file.** Claims run
  from 1978; policies do not. Every ratio query is therefore windowed to
  2009-2025. Losses before that window have no denominator and must not be
  turned into a loss ratio.
- **Nominal dollars.** Amounts are not inflation-adjusted. Comparisons across
  distant years are comparisons of nominal dollars, and the analysis windows
  accordingly rather than pretending otherwise.
- **Risk Rating 2.0 breaks premium comparability.** FEMA changed the pricing
  methodology from October 2021. Premium before and after that date is not
  generated by the same process, so a premium trend line spanning it is
  measuring a methodology change as much as a risk change.
- **`causeOfDamage` is multi-valued.** FEMA allows more than one cause code
  per claim, so raw values include combinations like `2D`. Grouping on it
  directly returns combination strings, not categories. Split and unnest first.
- **Redaction.** Latitude and longitude are approximate and deliberately
  coarsened. No analysis here goes below county or ZIP level, and nothing
  attempts to re-identify a property - that is prohibited by FEMA's terms.

## Repo layout

```
src/fetch_schema.py     pull live field definitions from FEMA
src/download_data.py    resumable bulk parquet download
src/build_db.py         DuckDB warehouse: fact_claims, agg_policy_exposure, mart_loss_ratio
src/run_analysis.py     run sql/, write Tableau extracts
notebooks/01_eda.py     exploratory pass, writes outputs/eda_report.md
sql/                    five analysis queries, one per business question
docs/DATA_DICTIONARY.md verified field and code reference
outputs/                CSV extracts consumed by the dashboard
```

## The five questions

| Query | Question |
|---|---|
| `01_loss_ratio_by_segment` | Which segments lose money, and is it frequency or severity? |
| `02_claim_cycle_time` | How long does settlement take, and where is it slowest? |
| `03_underinsurance` | How often does damage exceed the coverage bought? |
| `04_denial_analysis` | When a claim closes unpaid, why - and is it the policy working or an expectation gap? |
| `05_sfha_paradox` | What share of paid losses sits outside the mapped high-risk zone? |
